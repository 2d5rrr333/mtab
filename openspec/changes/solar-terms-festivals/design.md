# Design: solar-terms-festivals

## Context

lunar 包已具备 solar_to_lunar / weekday_name / ganzhi / 闰月（1900–2100，移植自 solarlunar）。clock-widget 的日期行由 store 的 `clock_view_for` 派生（init 与 tick_date 时），JS 只做拼接。本 change 是纯派生扩展：无 config、无事件、无迁移。

## Goals / Non-Goals

**Goals:**

- 二十四节气用寿星通用公式（天文算法：太阳视黄经）计算，1900–2100 全范围与权威万年历一致
- 节日表覆盖农历传统节日（含除夕）+ 公历法定节假日
- 节日优先展示；ClockView 扩展两个可选字段，桥协议响应自动携带
- 全部新增逻辑在 MoonBit，测试锚定已知节气/节日日

**Non-Goals:**

- 节气时刻（几时几分）——只判定"当日是否节气日"，不显示时刻
- 节日倒计时、放假安排（调休）、节气科普卡片
- 用户自定义节日

## Decisions

### D1. 节气算法：寿星通用公式（太阳黄经法）

判定思路：对日期 D，计算 D 当日与 D+1 当日太阳视黄经所在的"节气区间"——若 D+1 的黄经跨过 15° 的整数倍 k×15°（k=0..23 对应春分…惊蛰），则 D 是第 k 个节气日。

```
step(y, m, d) = 当日所在的节气序号（黄经 ÷ 15 向下取整）
is_term_day(D) = step(D) != step(D+1)   // 黄经在本日内跨过整数倍 15°
term_name(D)  = 跨过的那个 15° 倍数对应的节气名
```

- **核心函数**：`sun_longitude(jd)` —— 寿星公式：儒略世纪数 T → 太阳平黄经/平近点角 → 地心黄经的周期项（VB 项，取至 0.000001° 精度的前若干阶）+ 光行差 + 章动（本范围精度需求下可取主项）
- **儒略日**：由 `days_from_civil`（已有）直接换算 JD = days + 2440587.5（UTC 0 点起算；节气时刻的时区影响 ±14h，对"当日判定"可能造成 ±1 日边界误差——**用东八区时间判定**：JD 计算 +8h/24 再取日界，见 D2 验证策略）
- **精度预算**：寿星公式截断至 v2 常数集，误差 << 1 分钟，远超 ±1 日需求；wasm IEEE-754 双精度确定性无虞
- **出处标注**：算法源自寿星天文历（许剑伟）公开的通用公式，源码头部注明；公式本身为数学事实，无许可争议

备选（否决）：`[Y×D + C]` 取整近似公式——边界年份（如 1987、2058 附近）误差可达 1 天以上，需逐年验证兜底，反而更费；查表 1900–2100 每年 24 值 = 4800+ 项数据，膨胀且无算法价值。

### D2. 时区与日界：按东八区判定

节气天文时刻是瞬时的，"落在哪一天"依赖时区。目标用户为中国时区，判定统一用 UTC+8：`jd_cn(D) = days_from_civil(D) + 2440587.5 + 8/24`，D 与 D+1 的黄经均取东八区当日 0 点。测试锚定全部用北京时间的已知节气日（如 2025-10-08 寒露）。

### D3. 节气名表与序号

`term_names[0..23]` 按黄经 0° 起算（春分=0°，0x15° 顺时针）：春分、清明、谷雨、立夏、小满、芒种、夏至、小暑、大暑、立秋、处暑、白露、秋分、寒露、霜降、立冬、小雪、大雪、冬至、小寒、大寒、立春、雨水、惊蛰。`step` 值直接索引（mod 24 归一）。

### D4. 节日表：两级查表

- **公历**：`(month, day) -> name`——1/1 元旦、5/1 劳动节、10/1 国庆节（含法定主要节日）
- **农历**：`(month, day, is_leap) -> name`——正月初一 春节、正月十五 元宵节、五月初五 端午节、七月初七 七夕节、八月十五 中秋节、九月初九 重阳节；**除夕**= 农历十二月最后一天（腊月廿九或三十：次日为次年正月初一即除夕）
- 闰月日不视为节日（闰五月不重过端午）
- 纯静态表 + O(1) 查找，无状态

### D5. ClockView 扩展与展示优先级

```
ClockView { weekday, lunar, solar_term : String?, festival : String? }
date-line = [公历, 星期] + (festival ?? solar_term ?? 无) + [农历]
```

- `clock_view_for` 内：先算 festival（公历表 → 农历表 → 除夕判定），非节日再算节气
- ToJson 自动携带两个新字段（`solarTerm`/`festival`），JS 拼接时 null 跳过——旧 JS 读新响应无感（未知字段忽略）
- 超出农历范围（lunar=None）时节日/节气也置 None，公历与星期照常（既有降级行为不变）

### D6. 验证策略（四层）

- `moon test`：节气锚定——每年抽 2–4 个已知节气日（含 1987/2058 这类近似公式易错的年份）+ 每年 24 节气总数恰好 24 个的循环不变量（抽 5 个年份全年扫描）+ 非节气日 None + 边界（1900-02、2100-12）+ 除夕（腊月廿九的年份，如 2029 除夕=2月2日？以万年历核对的具体年份锚定）
- e2e：init 固定日期（2025-01-29 春节 + 2025-10-08 寒露两个 instance）断言响应字段
- harness：真实渲染 date-line 文本含节日/节气
- 回归：63 项 moon test、25 e2e、73/75 harness 不回退

## Risks / Trade-offs

- [寿星公式实现笔误导致跨年系统性偏移] → 锚定测试覆盖不同年代（1900s/1950s/2000s/2050s/2090s），任何一处错都立刻暴露
- [节气时刻恰在日界附近（北京时间 0 点前后）造成 ±1 日] → 锚定集里专门包含已知日界敏感案例（如 2021-02-03 立春 22:59）；公式精度远高于 1 日，判定与权威万年历一致即为目标
- [wasm 双精度与参考实现的舍入差异] → 黄经比较用区间跨越判定（step(D) != step(D+1)），对亚毫度级舍入不敏感
- [ClockView 新字段破坏旧 JS] → 字段可选、旧消费者忽略未知字段；本仓库 JS 同步更新
